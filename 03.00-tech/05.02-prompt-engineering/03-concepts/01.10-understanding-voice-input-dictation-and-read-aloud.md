# Understanding voice input, dictation, and read-aloud

Every input mechanism covered so far in this series assumes you're typing. Prompt files, instruction files, agent definitions — all of them shape what happens *after* text reaches the model. Voice changes how the text gets there in the first place.

<mark>Voice in VS Code</mark> is not one feature. It's four surfaces — editor dictation, terminal voice, voice chat, and read-aloud text-to-speech — that share an engine and a set of turn-control rules. As of VS Code 1.131 (Insiders), that engine is moving from a marketplace extension into the editor itself. This article explains what each surface does, what the delivery-model change means in practice, and what to re-check in a setup that already had voice working.

## 🎯 What voice actually does in VS Code

Four distinct surfaces, each with its own entry point.

| Surface | What it does | Where it lands |
|---|---|---|
| **Editor dictation** | Speech becomes text in the active editor | The file you're editing |
| **Terminal voice** | Speech becomes a terminal command or input | The active terminal |
| **Voice chat** | Speech becomes a chat prompt | Chat view, inline chat, or quick chat |
| **Read-aloud (TTS)** | Chat responses are spoken back to you | Your speakers |

Dictation isn't limited to code files. It also works in the source-control commit input box and in pull-request comment fields — the places where you write prose inside the editor rather than outside it.

Voice chat has several entry points because the chat surfaces do: there's a voice equivalent for the chat view, for inline chat, and for quick chat. Which one you use determines where the answer appears, not how the speech is captured.

Read-aloud is the reverse direction. A chat response can be spoken automatically, or on demand via a speaker icon on the response. Pressing Escape interrupts playback.

## 🏗️ The delivery model, before and after

Until VS Code 1.131, all of this came from the **VS Code Speech** marketplace extension. You installed it, and voice commands appeared. Each supported language shipped as its own extension pack — 26 of them.

VS Code 1.131 (Insiders) changes who provides the engine. Built-in on-device dictation now covers editor dictation and terminal voice, and adds read-aloud text-to-speech. Alongside it, extension-provided voice mode disables itself automatically when built-in voice mode is in use.

| Before (extension era) | After (built-in, 1.131 Insiders) |
|---|---|
| Voice required installing VS Code Speech | Voice ships with the editor |
| Per-language extension packs | Handled by the built-in engine |
| Terminal dictation wasn't available | Terminal voice is a supported surface |
| Read-aloud existed in chat only | Read-aloud is a general capability |
| Two voice providers could compete for the microphone | The extension stands down automatically |

### The pattern behind the change

This is the second time in two releases that VS Code has absorbed a capability out of the extension model. In 1.130, agent sessions moved out of the extension host into a dedicated **Agent Host** process with an open protocol. In 1.131, voice moves out of a marketplace extension into the editor.

Both changes follow the same shape: a capability proves itself as an extension, then gets pulled into the product, and the extension becomes the compatibility path rather than the delivery path. Recognising the pattern is useful because it predicts the friction. When a capability moves house, two things follow — surfaces that used to share code drift apart and need parity fixes, and setups that depended on the old provider need re-checking.

## 🔒 Why on-device matters

The extension-era documentation is explicit about this: voice support doesn't require you to be online, recordings are never sent to an online service, and recognition is computed locally on your machine.

That property is the reason voice is usable at all in a lot of professional contexts. Dictating into an editor means speaking the contents of files you may not be permitted to send anywhere — customer names in test fixtures, internal service endpoints, unreleased product terminology. A cloud speech service turns every dictation session into a data-transfer question. A local one doesn't.

It also means voice keeps working on a plane, on a bad hotel connection, or behind a network policy that blocks the speech endpoint. The trade-off is model size and accuracy ceiling: on-device recognition has less headroom than a large hosted model, which is exactly why the transcript-quality work described below matters so much.

Treat "on-device" as the property to verify rather than assume as the built-in stack settles — it's a documented characteristic of the extension implementation, and the built-in release notes describe the new dictation as on-device too.

## ✍️ What makes a transcript usable

Raw speech-to-text produces something that reads like a transcript. Writing needs something else. VS Code 1.131 ships three changes that all attack the same gap:

- **Incremental cleanup while you speak.** Punctuation and phrasing refinements appear during a long dictation session instead of arriving in one pass at the end. You can see what you're producing while you produce it, which means you can correct course mid-paragraph.
- **List formatting in post-processing.** Spoken bullets and numbered items come out as real Markdown lists. Structure you intended survives instead of collapsing into a run-on paragraph.
- **Filler-word filtering.** "Um" and "uh" are dropped before they reach the buffer.

Individually these are cosmetic. Together they change which workloads dictation can carry.

| Workload | Before | After |
|---|---|---|
| Short chat prompt | Worked fine | Works fine |
| Terminal command | Not supported | Supported |
| Paragraph of documentation | Heavy cleanup afterwards | Usable first draft |
| Structured notes with lists | Structure lost | Structure preserved |

The practical test is whether dictating is faster than typing *including* the edit pass afterwards. For a one-line prompt it always was. For a paragraph it usually wasn't, because the cleanup cost more than the typing saved. That's the balance these changes shift.

## ⚙️ Turn control: hands-free versus explicit send

The hardest problem in voice input isn't recognition. It's knowing when you've finished talking.

VS Code offers several answers:

- **Walky-talky mode** — press and hold to speak. Releasing stops recognition and submits the turn. Unambiguous, but it occupies a hand.
- **Silence detection** — a pause of a configured length submits automatically. Convenient in conversation, hostile when you're thinking mid-sentence.
- **Stop phrase** — you say a specific phrase to send.
- **Explicit send** — the turn stays open until you send it yourself.
- **Keyword activation** — "Hey Code" starts listening without a keystroke, with a status-bar microphone indicator showing when the editor is listening.

VS Code 1.131 changes the default relationship between these. With hands-free mode disabled, a Voice Mode turn now **stays open** unless you explicitly configure silence detection or a stop phrase to send it.

This is the one change in the release most likely to surprise an existing user. If your workflow relied on pausing to send a message, that behaviour is now opt-in. Nothing is broken — the turn is waiting for you — but the message you thought you sent is still sitting in the input box.

There's a deeper point here worth internalising. Auto-send on silence and thinking out loud are fundamentally incompatible. A prompt worth dictating is usually a prompt worth pausing in the middle of. Defaulting to an open turn is the right call for prompt engineering specifically, even where it's the wrong call for casual conversation.

## 🔍 What to re-check in an existing setup

The automatic stand-down of extension-provided voice mode is a change that alters a working configuration without being asked to. That makes it worth a deliberate pass.

| Check | Why |
|---|---|
| **Which provider is handling your microphone** | The extension may have disabled itself. Confirm which engine is active before concluding voice is broken |
| **Whether your voice keybindings still fire** | Command IDs may differ between extension and built-in implementations |
| **Whether your turn-send behaviour changed** | An open turn where you expected auto-send is the most likely surprise |
| **Which microphone is selected** | Microphone selection moved into quick actions on the voice buttons, replacing the separate configuration gear |
| **Your language setting** | Language selection previously came from per-language extension packs |
| **Whether you still need the extension** | On an Insiders build with built-in voice working, the extension may be redundant. On stable, it isn't |

If voice stops working entirely after an update, check provider selection before checking settings. A silent hand-over between two working implementations looks identical to a broken one.

## ⚠️ Where the documentation is still behind

Be careful with settings names right now.

The published voice documentation describes the **extension-based** implementation. Its setting keys — the `accessibility.voice.*` family covering keyword activation, speech timeout, auto-synthesis, and speech language — belong to that implementation. The VS Code 1.131 release notes describe the built-in behaviour but don't name any setting IDs.

That leaves an open question that can't be answered from published sources: whether the built-in stack reuses the same keys, introduces new ones, or splits them. Until the documentation catches up, the honest position is to describe what the features *do* and let the settings UI tell you what they're called. Searching "voice" or "dictation" in settings is more reliable than copying a key from an article written for the previous delivery model.

Two related behaviours are documented for the extension era and not yet confirmed for the built-in stack: **walky-talky mode** and **"Hey Code" keyword activation**. Both are useful. Neither should be assumed to survive the move unchanged.

Finally, remember that 1.131 is an **Insiders** release. Everything described here as new can still change before it reaches stable.

## 🎯 Conclusion

Voice is a fourth input modality alongside typing, selection, and file references — and as of VS Code 1.131 it's part of the editor rather than an add-on.

### Key takeaways

- **Four surfaces, one engine** — editor dictation, terminal voice, voice chat, and read-aloud share recognition and turn-control behaviour
- **Delivery moved, not capability** — most of this existed as an extension; what changed is who ships it
- **On-device is the enabling property** — local recognition is what makes dictating real code and real customer data possible
- **Transcript quality decides the workload** — incremental cleanup, list formatting, and filler filtering are what move dictation from prompts to paragraphs
- **Turn control is the real design problem** — an open turn by default suits thinking out loud; auto-send suits conversation
- **Re-check an existing setup** — the extension stands down automatically, which can look like breakage
- **Don't trust setting names yet** — published keys describe the extension era; use the settings UI
