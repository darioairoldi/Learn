# Validation sequence — SignalR real-time navigation metadata push

Validates that a content change (add/remove article) propagates to the live navigation
counts **without a full page reload and without client polling**, using the new SignalR
`NavHub` push, and that the server-side recompute is limited to the **changed root branch**
(not the whole content tree).

## Performance evidence

Before the subtree-scoping fix, `NavChangePublisher.FlushAsync` recomputed the entire
content tree on every change:

```text
NavChangePublisher.FlushAsync END   69.2s
NavChangePublisher.FlushAsync END   28.5s
```

After scoping the recompute to only the changed root branch
(`DynamicNavBuilder.RecomputeSubtreeAsync`):

```text
DynamicNavBuilder.RecomputeSubtreeAsync END   172m   (05.00-issues branch only)
NavChangePublisher.FlushAsync END            1650m   (subtree walk + 500ms debounce + cache invalidation + broadcast)
DynamicNavBuilder.RecomputeSubtreeAsync END   226m
NavChangePublisher.FlushAsync END            1301m
```

The actual tree work dropped from ~69 s to ~0.2 s (~300×); end-to-end publish latency
(including the 500 ms debounce and cache eviction) is ~1.3–1.6 s, comfortably within the
real-time-feel budget.

## Notes

- SignalR replaces the previous two client polling loops (version-poll and counts-converge).
  The version poll was removed; the hub's `MetadataChanged` / `CountsReady` events drive the
  client, with `WithAutomaticReconnect()` for robustness.
- The temporary demo article was deleted at the end of the run (verified `Test-Path = False`);
  it is not committed.
- The remaining ~1.3 s of `FlushAsync` is dominated by the 500 ms debounce plus SmartCache
  eviction of all nav-level keys (`InvalidateLevels`). Further trimming (targeted level
  eviction, reduced per-file Diginsight logging) is parked to plan 00.03 (PL-3).

## Result

**PASS** — real-time add/remove propagation confirmed in both directions; server-side
recompute confirmed limited to the changed branch and sub-second.
