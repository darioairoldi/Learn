## 📝 Description

`Learn.Web` caches Markdown source bytes through a Diginsight **SmartCache** decorator,
`CachedContentSource`, wrapping the underlying `IContentSource` (filesystem in dev, blob in prod).
While reviewing the caching behaviour we asked a simple question:

> When two requests hit SmartCache for the **same key** and both miss, is the origin fetched once or twice?

Reading the SmartCache source (`SmartCache.GetAsync`) confirmed the answer: **SmartCache does not
coalesce concurrent (racing) cache misses.** Two overlapping misses for the same key each invoke the
fetch delegate and therefore each hit the origin. This is the classic **cache-stampede** pattern.

The same is true **across nodes** in a distributed deployment: SmartCache's cross-node awareness is
populated *after* a value is written and broadcast, so a genuinely simultaneous multi-node miss also
fetches once per node.

**Impact:**

- 🔸 On a cold key (startup, after invalidation, or after expiry), N concurrent requests for the same
  Markdown page trigger **N origin reads** instead of 1.
- 🔸 In `Learn.Web` the origin is a filesystem/blob read — cheap individually, but the site issues
  **many concurrent same-key reads** during prerender (sidebar + both top-bar halves + page body),
  so the amplification is real on the cold path.
- 🟢 No correctness bug — results are identical; the cost is redundant work, not wrong data.

**Scope note:** This document analyses the SmartCache behaviour and implements a **local** fix in
`Learn.Web` (in-process coalescing in `CachedContentSource`). Adding racing-miss coalescing to the
SmartCache library itself is tracked as a **separate follow-up**.

## 🔬 Analysis

### Root cause

`SmartCache.GetAsync<T>` (private overload) resolves a miss through a local function
`FetchAndSetValueAsync`, which calls the caller's `fetchAsync` delegate directly and then `SetValue`:

```csharp
async Task<T> FetchAndSetValueAsync(Activity? activity)
{
    ...
    value = await fetchAsync(cancellationToken);   // caller delegate → origin
    ...
    SetValue(keyHolder, value, timestamp, ...);    // store + notify AFTER fetch
    return value;
}
```

There is **no** in-flight registry (no `ConcurrentDictionary<key, Task<T>>`, no `Lazy<Task<T>>`, no
per-key `SemaphoreSlim`) guarding the fetch. A grep of the whole `Diginsight.SmartCache` project for
`inflight` / `pending` / `GetOrAdd(Task)` / `Lazy<` / `SemaphoreSlim` / `stampede` returns nothing on
the fetch path. Therefore **concurrent misses for one key each execute `fetchAsync`.**

### Why the distributed layer does not help a *simultaneous* race

SmartCache's cross-node behaviour is **asynchronous and post-write**:

1. Each node has its own in-memory `MemoryCache`.
2. On a completed fetch, `SetValue` → `NotifyMiss` (InMemory / MixedPassive) or `WriteToLocation` →
   Redis (PurePassive) **broadcasts** "I now have key K, created at T".
3. Peers populate their `externalMissDictionary` from that broadcast.
4. A *later* miss consults `externalMissDictionary` first and, if a peer/Redis holds a fresh entry,
   fetches from there (via `TaskUtils.WhenAnyValid`, racing **locations** by latency) instead of the
   origin.

The coordination in step 3 happens **only after** step 2 completes and the message propagates — it is
**not a distributed lock taken before the fetch**. So in a true simultaneous race:

| | Node A | Node B |
|---|---|---|
| t0 | local miss; `externalMissDictionary` empty | local miss; `externalMissDictionary` empty |
| t1 | `fetchAsync` → **origin** | `fetchAsync` → **origin** |
| t2 | `SetValue` → broadcast | `SetValue` → broadcast |
| t3 | receives B's broadcast (too late) | receives A's broadcast (too late) |

Both fetch. The distributed layer de-duplicates **staggered** requests (a warm peer serves later
misses) and propagates **invalidation** — it does not collapse a **simultaneous** multi-node miss.

> ⚠️ `TaskUtils.WhenAnyValid` looks like concurrency control but it races **cache locations** for a
> single caller's request; it does not de-duplicate **concurrent callers**.

### Impact assessment

| Dimension | Assessment |
|-----------|------------|
| Correctness | ✅ Unaffected — identical results |
| Cold-path cost | 🔸 N× origin reads for N concurrent same-key misses |
| Warm-path cost | 🟢 None — hits return from memory |
| Current deployment | 🔸 Single-node; only the in-process race applies (Redis not configured) |
| Blast radius | Content reads via `CachedContentSource`; navigation is already protected (see below) |

### Why navigation was already safe

`DynamicNavBuilder` **already** coalesces concurrent misses per cache key with
`ConcurrentDictionary<string, Task<...>>` + `GetOrAdd` (`_childrenInFlight` / `_indexInFlight`). Only
the **content-byte** path through `CachedContentSource` lacked equivalent protection.

## ✅ Solution Implemented

### Fix — in-process coalescing in `CachedContentSource`

Added a per-key in-flight registry mirroring the proven `DynamicNavBuilder` pattern. Concurrent
identical requests now share **one** `smartCache.GetAsync` call (and therefore at most one origin
fetch); the shared task runs under `CancellationToken.None` so one caller cancelling cannot abort the
fetch the others are awaiting.

```csharp
// Coalesces concurrent identical fetches per content key. SmartCache has no in-flight
// de-duplication, so without this two simultaneous misses for the same key would each run the
// fetch delegate and hit the origin (blob/file). Concurrent callers share one Task instead.
private readonly ConcurrentDictionary<string, Task<CachedContent>> _inFlight = new();

public async Task<ContentResult?> GetAsync(string contentKey, CancellationToken ct = default)
{
    using var activity = Observability.ActivitySource.StartMethodActivity(logger, new { contentKey });

    if (!IsCacheable(contentKey))
    {
        return await inner.GetAsync(contentKey, ct);   // binary assets bypass the cache
    }

    // Cache-stampede avoidance. Shared task uses CancellationToken.None; each caller observes its
    // own token via WaitAsync.
    Task<CachedContent> inFlight = _inFlight.GetOrAdd(contentKey, FetchThroughCacheAsync);
    try
    {
        CachedContent envelope = await inFlight.WaitAsync(ct);
        return envelope.Result;
    }
    finally
    {
        _inFlight.TryRemove(new KeyValuePair<string, Task<CachedContent>>(contentKey, inFlight));
    }
}

private async Task<CachedContent> FetchThroughCacheAsync(string contentKey)
{
    var options = new SmartCacheOperationOptions();
    var key = new MethodCallCacheKey(cacheKeyService, typeof(CachedContentSource), nameof(GetAsync), contentKey);

    return await smartCache.GetAsync(
        key,
        async innerCt => new CachedContent(await inner.GetAsync(contentKey, innerCt)),
        options,
        callerType: typeof(CachedContentSource),
        cancellationToken: CancellationToken.None);
}
```

### Solution features

| Feature | Behaviour |
|---------|-----------|
| **Per-key coalescing** | Concurrent same-key requests share one `smartCache.GetAsync` → one origin fetch |
| **Cancellation isolation** | Shared fetch runs under `CancellationToken.None`; callers use `WaitAsync(ct)` |
| **Hit path unchanged** | On a memory hit the shared task completes immediately; entry removed right after |
| **Binary bypass preserved** | Non-Markdown keys still short-circuit to `inner` before the registry |
| **Scope** | In-process only — collapses **same-node** races (the case that applies today) |

### What this fix does **not** do

- ❌ It does not coalesce a **cross-node** simultaneous race (needs a distributed lock, e.g. Redis
  `SET NX`/RedLock, or library-level support).
- ❌ It does not change SmartCache itself — the library still fetches per concurrent miss.

## 📚 Additional Information

### Testing recommendations

- [ ] Unit test: fire N concurrent `GetAsync(sameKey)` against a stub `inner` that counts calls and
      blocks until released; assert `inner` is invoked **once**.
- [ ] Verify a faulted fetch propagates to all coalesced awaiters and the key is removed from
      `_inFlight` (no poisoned entry).
- [ ] Verify per-caller cancellation: one caller cancels, others still receive the value.

### Performance impact

- Cold path: origin reads for a hot key drop from **N → 1** under concurrency.
- Warm path: negligible overhead (one `ConcurrentDictionary` `GetOrAdd`/`TryRemove` per call).

### Follow-up — SmartCache library

Add optional **racing-miss coalescing** inside `SmartCache.GetAsync` (in-process de-duplication of
concurrent misses per key), and consider an opt-in **distributed** single-flight (Redis lock) for
multi-node stampede protection. Tracked separately.

## 🎓 Lessons Learned

**What went wrong:**

- An in-memory cache in front of an expensive origin was assumed to also provide **stampede
  protection**. It does not — `MemoryCache`-style caches (and SmartCache on top) de-duplicate
  **storage**, not **concurrent misses**.

**What went right:**

- The project already had the correct pattern in `DynamicNavBuilder`; reusing it made the fix small,
  consistent, and low-risk.
- Reading the library source (rather than assuming) produced a precise, testable root cause and
  clarified the exact distributed semantics.

**Improvements for the future:**

- When wrapping any expensive origin behind a cache, decide explicitly whether **single-flight**
  (coalescing) is required, and add it at the decorator boundary.
- Distinguish three separate concerns when reasoning about distributed caches: **storage**,
  **invalidation propagation**, and **stampede protection** — a library may provide some but not all.

## 📎 Appendix

### A. Coalescing vs. related concepts

| Concept | Provided by | De-duplicates |
|---------|-------------|---------------|
| In-process coalescing (single-flight) | `DynamicNavBuilder`, now `CachedContentSource` | Concurrent **callers**, same node, same key |
| Location race (`WhenAnyValid`) | SmartCache | Cache **locations** for one caller (fastest wins) |
| Cross-node awareness | SmartCache companion (Service Bus / Redis) | **Staggered** misses (post-write), + invalidation |
| Distributed single-flight | *not implemented* | Concurrent **callers across nodes** |

### B. Key source references

```text
SmartCache.GetAsync (private)      → FetchAndSetValueAsync → fetchAsync (no in-flight guard)
SmartCache.SetValue                → NotifyMiss / WriteToLocation (post-write broadcast)
externalMissDictionary             → populated from peer broadcasts (eventual)
TaskUtils.WhenAnyValid             → races locations, not callers
DynamicNavBuilder                  → _childrenInFlight / _indexInFlight (reference pattern)
```
