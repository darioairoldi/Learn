# Navigation ordering: persisted, drag-and-drop reordering of sections and mounts

> **Status: draft.** Design + investigation plan. Investigation is complete; the recommended
> approach and phases are **proposals** pending the [§ Open decisions](#-open-decisions). Parent:
> [strat-review overview](overview.md) · [mount plan](00.01-learning-hub-improvements-mount-plan.md).

---

## 🎯 Goal

Decide **how mounts sort relative to curated sections** and, more broadly, specify a **persisted
ordering** mechanism that supports **OneNote-style drag-and-drop reordering** — where an authorized
user drags a notebook/section to a preferred position and the order sticks.

## 🧭 Motivation

Today, order is *derived* from names (numeric prefix, date) — deliberate but rigid: changing order
means renaming folders. OneNote lets you drag a notebook or section to any position and the ordering
persists in the backing store. For a multi-source site (curated content **plus** mounts), the owner
needs the same freedom to interleave and reorder top-level nodes without renaming files.

## 🔎 Investigation: how ordering works today (✅ done)

- **Ordering is a `SortTuple(Group, Num, Text)`.** `NavRules.SortKey` assigns: numeric-prefixed →
  `(0, value, name)` (ascending), date-prefixed → `(1, -date, "")` (newest first), else →
  `(2, 0, name)` (alphabetical). `DynamicNavBuilder.BuildLevelAsync` sorts by `Group`, then `Num`,
  then `Text`.
- **The only explicit override is `metadata.yml` `order:`**, which maps to `(0, order, name)` — i.e.
  it joins the numeric group. So a folder can already be given an explicit weight, but **per-folder**
  and only within the numeric band.
- **There is no write path.** `IContentSource`/`IContentLister` are read-only; nothing can persist a
  new order. Drag-and-drop therefore needs a **write capability** and a **persisted representation**.
- **Reordering N siblings by per-folder `order:` rewrites N files** — awkward for drag-and-drop.

## 🧩 Recommended approach: a per-parent ordering manifest (🟡 todo)

- **Persist order in one file per level, not per sibling.** Extend the **parent** folder's
  `metadata.yml` with an optional ordered `children:` list (child folder names / mount ids in the
  desired sequence), or a sibling `.order.yml`. Dragging reorders **one** manifest write — the OneNote
  model (the container owns its children's order). (🟡 todo — design decision)
- **Make the manifest the highest-priority sort signal.** `BuildLevelAsync` applies, in order:
  (1) explicit manifest position → `Group 0` ascending by listed index; (2) any child not listed →
  fall back to the current `SortKey`. So a partially-ordered manifest still works (listed items first,
  the rest by today's rules). (🟡 todo — design decision)
- **Mounts and curated folders share one top-level manifest.** Because a mount is just a named
  top-level node (plan 01), the root manifest can interleave curated folders **and** mount ids —
  answering *"how do mounts sort relative to curated sections?"*: **they don't get a reserved band by
  default; they participate in the same drag-orderable sequence.** A mount's `order` from its
  registry entry seeds its initial position; the manifest can then move it anywhere. (🟡 todo)
- **Writing needs `IContentWriter` + auth.** Reordering is an authorized owner/admin action, so it
  depends on the shared write path (see § Cross-cutting) and the auth work in plan 02. After a write,
  it triggers **scoped invalidation** for that prefix (plan 03 / 00.03). (🟡 todo)

## 🗺️ The OneNote analogy (✅ done)

| OneNote concept | Ordering equivalent |
|---|---|
| Drag a section to a new position | Drag a nav node; persist new index in the parent manifest |
| Order stored with the notebook | Order stored in the **parent** `metadata.yml` `children:` list |
| Sections + section groups reorder alike | Curated folders **and** mounts reorder in one sequence |
| New section appended at the end | Unlisted child falls back to name-derived `SortKey` |

## ⚙️ Cross-cutting dependency: a write path (🟡 todo)

Introduce `IContentWriter` (`PutAsync(key, bytes)`, `DeleteAsync(key)`) with filesystem and blob
implementations, **auth-gated**. This same capability is required by the documentation-manager
(plan 01), streams (plan 03), and ordering here — specify it once, reuse everywhere. (🟡 todo)

## 🪜 Proposed implementation phases (🟡 todo)

1. **Phase 0 — manifest read.** Teach `BuildLevelAsync` to honor a parent `children:` order list as
   the top-priority signal (read-only; hand-edited manifest). Proves the ordering model with no UI or
   write path. (🟡 todo)
2. **Phase 1 — write path.** Add `IContentWriter`; expose an authorized `POST /_nav/order` that
   rewrites a parent manifest and triggers scoped invalidation. (🟡 todo)
3. **Phase 2 — drag-and-drop UI.** Add drag handles in the sidebar (authorized users only) that call
   `POST /_nav/order`; optimistic reorder, confirmed on invalidation. (🟡 todo)

## ❓ Open decisions

- **D1-manifest-vs-perfolder** — persist order in a **per-parent manifest** (recommended) or keep
  extending **per-folder `order:`**? *Resolves:* user preference; manifest is fewer writes but a new
  concept. *Gates:* Phase 0 shape.
- **D2-reorder-scope** — is drag-and-drop for the **owner/admin only**, or also for a documentation-
  manager persona per mount? *Resolves:* user; feeds the auth model (plan 02). *Gates:* Phase 2.
- **D3-mount-band** — confirm mounts **interleave** with curated content (recommended) rather than
  occupying a **reserved trailing band**. *Resolves:* user. *Gates:* root manifest semantics.

## 🔭 Discovery

- **DS1-manifest-drift** — a manifest may list a child that no longer exists, or omit a new one.
  *At build time* → ignore missing entries; append unlisted children via `SortKey`. Never fail the
  level over a stale manifest.

## 🅿️ Park lot

- **Cross-level drag** (moving a folder into a different parent) — that is a *content move*, not a
  reorder. → `defer`
- **Per-user personal ordering** (each reader's own order) — conflicts with a shared site. → `closed: out of scope for a shared site`
- **Reordering articles within a folder** (vs. folders) — same manifest mechanism, later. → `defer`
