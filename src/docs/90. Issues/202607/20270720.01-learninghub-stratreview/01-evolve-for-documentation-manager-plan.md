# Evolve for the documentation-manager: autonomous docs for software projects, rendered live

> **Status: draft.** Design + investigation plan. Investigation is complete; the recommended
> approach and phases are **proposals** pending the [§ Open decisions](#-open-decisions). Parent:
> [strat-review overview](overview.md) · builds on the four `00.0x` technical plans.

---

## 🎯 Goal

Evolve the current architecture toward **full support for autonomous documentation creation and
rendering for software projects**: let the renderer host a `docs/`-style tree produced by a
**documentation-manager stream** so that **runtime rendering replaces the static build**. Because the
same renderer will serve *different* software projects, **ease of UI customization is a first-class
requirement**.

## 🧭 Motivation

A `documentation-manager` agent is **already designed** (see
[00.documentationmanager.design.md](../../../../../06.00-idea/autonomous-streams/reverse-engineering/00.documentationmanager.design.md)):
it reads a repository's code, config, IaC, pipelines, and schema, and emits a structured Markdown
site for four audiences (developers, architects, operations, security). Today that design terminates
in a **static MkDocs build + Azure SWA deploy**
([10.design-static-site.md](../../../../../06.00-idea/autonomous-streams/reverse-engineering/10.design-static-site.md)).
The Learning Hub already renders Markdown on demand with runtime navigation — so the static build is
redundant. Retargeting the agent's output to a **Learn.Web mount** removes the build entirely and
makes generated docs live the moment they land.

## 🔎 Investigation: what exists vs. what is missing (✅ done)

- **The producer exists.** The documentation-manager design already defines the taxonomy, discovery,
  nav governance, and per-area templates — it emits governed Markdown with a folder structure and
  branding. Its current *sink* is MkDocs.
- **The host exists.** `Learn.Web` renders any Markdown on demand and builds nav from folder
  hierarchy + `metadata.yml`. A generated tree needs **no build** to render here.
- **The connection is missing.** Three gaps: (1) **hosting** a second tree → the **mount** mechanism
  (plan 00.01); (2) **publishing** into it → a **write path** (`IContentWriter`, plan 00.02
  § Cross-cutting); (3) **freshness** → **scoped invalidation** (plan 00.03).
- **Per-project identity is thin.** UI customization today = `metadata.yml` (labels/icons/order) +
  `ThemeState` (theme picker). There is no **per-mount site profile** (title, logo, accent theme,
  top-bar, home layout) — essential when one renderer serves many projects' docs.

## 🧩 Recommended approach: retarget the agent to a Learn.Web mount + per-project profile (🟡 todo)

- **Retarget the sink.** The documentation-manager emits its tree into a **mount location** (blob
  prefix / folder) instead of running `mkdocs build`. The nav it governs is expressed with the
  Learning Hub's `metadata.yml` conventions (which the agent already understands as "nav governance").
  Runtime rendering replaces the static build. (🟡 todo — design decision)
- **Publish = write + invalidate.** After a generation pass, the stream writes changed files via
  `IContentWriter` and calls scoped `POST /_nav/invalidate?prefix=<mount>`; the docs go live with no
  redeploy. (🟡 todo)
- **Per-project site profile (the UI-customization surface).** Introduce a per-mount
  `site.yml` (or extend the mount root `metadata.yml`) declaring **title, logo, accent/theme,
  top-bar links, home layout, and footer** — a **low/no-code** branding surface so each software
  project's docs render with its own identity **without touching renderer code**. The renderer reads
  the active mount's profile and applies it to the shell (`ThemeState` already proves runtime theming
  is feasible). (🟡 todo — design decision)
- **Preserve the four-audience taxonomy.** The agent's existing progressive-disclosure structure
  (Home → Getting Started → Architecture → Infrastructure → Reference → Components → Security →
  DevOps → Appendix) maps directly onto Learning Hub folders; no re-design of content shape. (🟡 todo)
- **Provenance + freshness banner.** Each generated mount carries a manifest (source commit,
  generated-at, generator id) surfaced as a "generated docs — as of X" banner so readers trust
  currency. (🟡 todo)

## 🗺️ From static build to live mount (✅ done)

| MkDocs (today) | Learn.Web mount (evolved) |
|---|---|
| `mkdocs build` → static HTML | On-demand Markdig rendering — **no build** |
| `mkdocs.yml` `nav:` | Folder hierarchy + `metadata.yml` (+ ordering manifest, plan 00.02) |
| Theme / branding block | Per-mount `site.yml` profile (title/logo/theme/top-bar) |
| Azure SWA deploy per change | Write to mount + scoped invalidate → live |
| One site per project (separate deploys) | Many projects as mounts on one renderer |

## 🪜 Proposed implementation phases (🟡 todo)

1. **Phase 0 — render a generated tree.** Place a documentation-manager sample output under a
   filesystem mount (plan 00.01 Phase 0) and confirm it renders + navigates with `metadata.yml`
   nav governance, no build. (🟡 todo)
2. **Phase 1 — publish pipeline.** Wire the write path + scoped invalidation so a generation pass
   publishes into a blob-backed mount and goes live. (🟡 todo)
3. **Phase 2 — per-project profile.** Implement `site.yml` branding/theming applied per active mount;
   validate two visually-distinct projects on one renderer. (🟡 todo)
4. **Phase 3 — autonomy.** Run the documentation-manager as a scheduled/triggered stream
   (generate → write → invalidate → verify) under the engine's reversible, gated discipline
   (plan 03). (🟡 todo)

## ❓ Open decisions

- **D1-profile-location** — put per-project UI config in a dedicated **`site.yml`** (recommended,
  clean separation) or **extend the mount root `metadata.yml`**? *Resolves:* user preference. *Gates:*
  Phase 2 shape.
- **D2-customization-depth** — for v1 is **theme + logo + title + top-bar** enough, or is a
  **pluggable home layout / custom components** needed per project? *Resolves:* how divergent the
  target projects' docs are. *Gates:* Phase 2 scope.
- **D3-agent-coupling** — should the documentation-manager emit **Learning-Hub-native `metadata.yml`
  directly**, or emit neutral output that a small **adapter** converts? *Resolves:* whether the agent
  stays sink-agnostic. *Gates:* Phase 0/1 boundary.

## 🔭 Discovery

- **DS1-mkdocs-residue** — the existing design references MkDocs-specific constructs (admonitions,
  `mkdocs.yml`). *During Phase 0* → catalog any Markdown that renders differently under Markdig and
  note the delta; adapt templates only where rendering actually diverges.

## 🅿️ Park lot

- **Search across a project's docs** (per-mount scoped search) — the flat index is global today. → `defer`
- **Versioned docs** (multiple versions of one project's docs mounted side by side). → `defer`
- **Two-way sync** (edits in the live site flowing back to the source repo). → `03-evolve-for-autonomous-streams-plan.md`
