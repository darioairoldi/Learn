# Cache invalidation: per-mount granularity and restoring the API-key guard

> **Status: draft.** Design + investigation plan. Investigation is complete; the recommended
> approach and phases are **proposals** pending the [§ Open decisions](#-open-decisions). Parent:
> [strat-review overview](overview.md). Contains a **security finding** (§ Investigation).

---

## 🎯 Goal

Specify **per-mount (per-prefix) cache invalidation** to replace the current global invalidation, so
publishing one mount does not rebuild the entire tree — and **restore the `InvalidateApiKey`
enforcement** that the endpoint currently omits.

## 🧭 Motivation

A documentation-manager stream (Layer ②) will publish to a single mount frequently. Today every
publish forces a full nav rebuild (the flat index walk alone is ~1.9 s). Scoped invalidation keeps
the rest of the tree hot. Separately, the invalidation endpoint is currently **unauthenticated**,
which is both a correctness regression and a mild denial-of-service vector.

## 🔎 Investigation: how invalidation works today (✅ done)

- **One global version, full clear.** `DynamicNavBuilder.Invalidate()` does
  `Interlocked.Increment(ref _version)` **and** `MemoryCache.Clear()`. Cache keys are
  `nav:{version}:{prefix}` and `navindex:{version}`, so bumping the version orphans *all* levels and
  the whole index at once.
- **`MemoryCache.Clear()` is a blunt instrument.** The same `IMemoryCache` is shared across the app
  (registered once via `AddMemoryCache()`), so a nav invalidation also evicts any unrelated cached
  data. Targeted eviction would be safer.
- **🔒 Security finding — the API-key guard was lost.** `ContentOptions.InvalidateApiKey` exists and
  the deploy workflows still set `Content__InvalidateApiKey` from the `LEARN_WEB_INVALIDATE_KEY`
  secret, **but** `NavEndpoints.Invalidate(DynamicNavBuilder, ILoggerFactory)` never reads the
  request or checks the key — it invalidates unconditionally. The recovered pre-Diginsight original
  (`.copilot/temp/diginsight-recover/Program.cs`) *did* enforce it with
  `CryptographicOperations.FixedTimeEquals`. The check must be restored. (✅ finding recorded)

## 🧩 Recommended approach: per-prefix versioning + targeted eviction (🟡 todo)

- **Per-prefix version map.** Replace the single `_version` with a small concurrent map
  `topSegment → version` plus a global fallback. Cache keys become
  `nav:{segmentVersion}:{prefix}`. Invalidating a mount/section bumps only that segment's version;
  sibling levels stay cached. (🟡 todo — design decision)
- **Targeted eviction, not `Clear()`.** Track the cache keys created per top segment (or rely on the
  version bump to orphan them and let sliding-expiration reclaim them) so a scoped invalidation never
  touches unrelated cache entries. (🟡 todo)
- **Index handling.** The flat index (`navindex`) is whole-tree. For v1, rebuild the index on **any**
  invalidation (keep a global index version) but debounce rapid successive publishes; a later phase
  can partition the index per top segment and stitch. (🟡 todo)
- **Scoped endpoint, back-compatible.** `POST /_nav/invalidate?prefix=<segment>` invalidates one
  segment; `POST /_nav/invalidate` with no prefix keeps the current global behavior. (🟡 todo)
- **Restore + require the key.** Re-add `InvalidateApiKey` enforcement using
  `CryptographicOperations.FixedTimeEquals`; when a key is configured it is **required** (reject with
  401 when missing/mismatched). When unset, keep dev-friendly open behavior **only** outside
  Production. (🟡 todo — security)

## 🪜 Proposed implementation phases (🟡 todo)

1. **Phase 0 — restore the guard.** Re-add `InvalidateApiKey` enforcement to the invalidate endpoint
   (`FixedTimeEquals`, 401 on mismatch). Independent, shippable, closes the security gap. (🟡 todo)
2. **Phase 1 — scoped endpoint.** Add `?prefix=` to `POST /_nav/invalidate`; introduce the per-prefix
   version map; keys become segment-versioned. (🟡 todo)
3. **Phase 2 — targeted eviction + index debounce.** Replace `MemoryCache.Clear()` with per-segment
   eviction; debounce index rebuilds under rapid publishing. (🟡 todo)

## ❓ Open decisions

- **D1-index-partitioning** — accept **whole-index rebuild** on any change for v1 (recommended,
  simpler) or **partition the index** per top segment now? *Resolves:* user tolerance for index
  rebuild latency vs. added complexity. *Gates:* Phase 2 scope.
- **D2-dev-open-invalidate** — when no key is configured, should invalidation stay **open in
  Development only** (recommended) or **always require** a key? *Resolves:* user. *Gates:* Phase 0
  behavior.

## 🔭 Discovery

- **DS1-mount-id-vs-segment** — a mount's `routePrefix` may be multi-segment (plan 01, D2). *At
  implementation* → key the version map by the **mount id** (from the composite) when the request
  targets a mount, falling back to the leading path segment for curated content.

## 🅿️ Park lot

- **Push invalidation to WASM clients** (so open browsers refresh nav live via SignalR). → `defer`
- **ETag/conditional-GET on `/_nav/*`** so clients can cheaply re-poll. → `defer`
- **Rate-limit the invalidate endpoint** as defense-in-depth beyond the key. → `defer`
