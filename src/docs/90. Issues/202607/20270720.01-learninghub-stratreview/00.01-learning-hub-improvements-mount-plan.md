## 🎯 Goal

Investigate and specify **how a mount configuration could work** so the renderer can host more than
one content tree — answering the open question *"are mounts static (`appsettings`) only, or also
discoverable at runtime?"* — using the OneDrive multi-location model as the reference experience.

## 🧭 Motivation

`Learn.Web` renders Markdown on demand and builds navigation at runtime, so "publishing" is just
"make the Markdown available." Today it can only see **one** source. A documentation-manager stream
(Layer ②) needs to attach additional generated trees **without a build or redeploy**. OneDrive shows
the target UX: several independently-connected locations, each with *Choose folders* and *Stop sync*,
plus *Add an account* at runtime.

## 🔎 Investigation: how content sources work today (✅ done)

Grounded in the current code:

- **One source, chosen by config.** `Program.cs` registers a single `AddSingleton<IContentSource>`
  that returns `FileSystemContentSource` or `BlobContentSource` based on `Content:Source`. The
  `IContentLister` registration casts *the same instance* (`sp.GetRequiredService<IContentSource>()`).
- **The contracts are read-only.** `IContentSource.GetAsync(contentKey)` returns bytes;
  `IContentLister.ListChildrenAsync(prefix)` + `ReadHeadAsync(key)` enumerate one level and sniff
  frontmatter. There is no write method.
- **Addressing is first-segment path routing.** A route maps to a content key
  (`Route()` strips `.md`/`.qmd`); `GetAsync` resolves that key against the one source.
- **Root infrastructure is already filtered.** `DynamicNavBuilder.RootInfra` excludes `src`,
  `deploy`, `docs`, `scripts`, `bin`, `obj`, `node_modules`, `99.00-temp` at the root — this is why
  `src/docs/…` never appears in the menu. A mount mechanism can reuse this pattern for a reserved
  mount namespace.
- **Config object.** `ContentOptions` holds `Source`, `NotFoundPath`, `InvalidateApiKey`, plus nested
  `Blob{AccountUri,ContainerName}` and `FileSystem{RootPath,WatchForChanges}`.

**Conclusion:** a mount is naturally modeled as *another `IContentSource`/`IContentLister` provider,
namespaced by a route prefix, composed behind the existing interfaces*. No renderer or nav code needs
to change to serve a mounted `.md` — only composition and configuration are new.

## 🧩 Recommended approach: composite, route-prefixed mounts (🟡 todo)

- **`CompositeContentSource`** — a new class implementing **both** `IContentSource` and
  `IContentLister`. It holds the **primary** source (curated content) plus an ordered list of
  **mounts**. `GetAsync(key)` and `ListChildrenAsync(prefix)` dispatch by matching the key/prefix's
  leading segment(s) to a mount's `routePrefix`; everything else falls through to the primary.
- **Each mount wraps an existing provider.** `FileSystemContentSource` and `BlobContentSource` are
  reused unchanged as the per-mount providers (a mount just points one of them at a sub-path / blob
  prefix). This keeps the path-traversal guards and frontmatter sniffing intact.
- **`MountOptions` shape** (bound from `Content:Mounts`):

  | Field | Meaning |
  |---|---|
  | `id` | Stable identifier (used by invalidation + the registry) |
  | `provider` | `fileSystem` \| `blob` |
  | `location` | Filesystem sub-path or blob prefix the provider reads |
  | `routePrefix` | Where the tree mounts in the route space (its top-level segment) |
  | `visibility` | `public` \| `private` (gates who may see it — see plan 02) |
  | `enabled` | `true`/`false` — *Stop sync* without deleting config |
  | `label` / `icon` / `order` | Optional nav overrides; else read the mount root's `metadata.yml` |

- **The nav integrates for free.** A mount's root `metadata.yml` (`label`/`icon`/`order`/`hidden`/
  `topbar-*`) slots it into the sidebar and top bar exactly like a curated folder, because
  `DynamicNavBuilder` already honors those keys.

## 🗺️ The OneDrive analogy (✅ done)

| OneDrive concept | Mount equivalent |
|---|---|
| A connected location (e.g. a library) | A **mount** (`id` + `provider` + `location`) |
| *Add an account* | Register a new mount **at runtime** (registry / admin API) |
| *Stop sync* | `enabled: false` |
| *Choose folders* | Optional per-mount include/exclude sub-paths (**§ Park lot** for v1) |
| Each location shown separately in Explorer | Each mount is its own top-level nav section |

## 🪜 Proposed implementation phases (🟡 todo)

1. **Phase 0 — static filesystem mount.** Add `Content:Mounts` binding + `CompositeContentSource`;
   compose one filesystem mount over the primary in dev; verify a mounted `.md` renders and appears
   in nav after `POST /_nav/invalidate`. Fully reversible. (🟡 todo)
2. **Phase 1 — static blob mount.** Point a mount at a blob prefix; confirm parity in the deployed
   site. (🟡 todo)
3. **Phase 2 — runtime registry.** Back mounts with a small persisted registry (seeded by the static
   config) and an **admin API** to add / remove / enable / disable a mount without redeploy — the
   *Add an account* / *Stop sync* experience. Gate the API behind auth (plan 02). (🟡 todo)
4. **Phase 3 — convention-discovered mounts.** A mount auto-appears when a well-known marker (e.g. a
   `mount.yml` at a reserved blob prefix) is present, so a documentation-manager stream can "connect"
   a tree by writing files alone. (🟡 todo)

## ❓ Open decisions

- **D1-config-surface** — ship **static-only** (Phases 0–1) first, or commit now to the **runtime
  registry** (Phase 2)? *Resolves:* user preference on whether non-developers add mounts. *Gates:*
  Phases 2–3.
- **D2-mount-namespace** — do mounts live under a **reserved top-level segment** (e.g. `/mounts/<id>`,
  mirroring `RootInfra`) or may a mount claim **any** top-level `routePrefix`? *Resolves:* user; also
  feeds the collision policy (plan 04). *Gates:* `routePrefix` validation.
- **D3-provider-set** — is `fileSystem` + `blob` sufficient for v1, or is an **HTTP/URL** provider
  needed (mount a remote docs endpoint)? *Resolves:* documentation-manager targets (plan 01).

## 🔭 Discovery

- **DS1-metadata-read-path** — a mount root's `metadata.yml` is read via `ReadHeadAsync("<prefix>/metadata.yml")`.
  *If a mount provider cannot cheaply range-read* (some blob layouts) → fall back to a full `GetAsync`
  of the metadata file only.
