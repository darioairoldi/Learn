## 🎯 Scope and goals

<mark>AICM</mark> (AI Cost Management) is the platform described in [the overview](00.000-overview.md): it reconciles cloud/vendor billing (the financial truth) with gateway and application telemetry (the attribution truth), then allocates AI cost across users, teams, companies, models, providers, and request types. This document defines the <mark>infrastructure and processing architecture</mark> that implements the [canonical Bronze/Silver/Gold schemas](02.000-bronze-silver-gold-schemas.md).

The v1 stance is <mark>start simple, scale out</mark>:

-   <mark>Bronze</mark> = a storage account (ADLS Gen2) that receives raw data from every source, append-only.
-   <mark>Silver</mark> = a set of .NET transformation jobs and APIs that normalize, enrich, and conform the raw files.
-   <mark>Gold</mark> = a multi-target serving layer: an Azure SQL star schema for chargeback and BI, with Azure Data Explorer (Kusto) and optionally Log Analytics for high-volume telemetry and dashboards.

Confirmed v1 choices (see [Key decisions](#-key-decisions)): .NET workers + Azure Functions on **App Service + WebJobs**, **mixed** batch + streaming ingestion, and a scale-out path to Microsoft Fabric, Container Apps, or AKS.

## 🧭 Design principles

1.  <mark>Two truths, never blended</mark>. Billing is financial truth; telemetry is attribution truth. They meet only through the allocation bridge (`fact_cost_allocation`).
2.  <mark>Immutable Bronze</mark>. Ingestion lands raw bytes unchanged and append-only. Silver and Gold are always rebuildable from Bronze.
3.  <mark>Pluggable connectors</mark>. Each source is an independent, uniformly shaped ingestion unit behind one contract, so adding Claude, Google, Cursor, or Databricks doesn't touch the core.
4.  <mark>Async, re-runnable stages</mark>. Ingestion never waits for processing; Silver and Gold are idempotent jobs triggered by data availability and safe to replay.
5.  <mark>Start simple, scale out</mark>. Everything ships first as .NET on App Service + WebJobs; heavy stages can later move to Fabric/Databricks without changing the canonical model.
6.  <mark>Contracts under version control</mark>. Canonical schemas, taxonomies, and allocation rules live in a versioned `contracts` area, not in code.
7.  <mark>Portable canonical model</mark>. Gold's star schema is the stable contract; alternative serving targets (Kusto, Log Analytics, Fabric) are additive, not replacements.

## 🥉 Bronze layer

Bronze is a single <mark>**ADLS Gen2 storage account**</mark> (**hierarchical namespace on**), one immutable landing zone for every source.

### Folder layout

Partition by **provider**, **dataset**, **scope**, and **date** so incremental loads and reprocessing are cheap:

``` text
bronze/
    azure/costmanagement/scope=<sub>/year=<yyyy>/month=<mm>/day=<dd>/*.parquet
    azure/gateway/          # Event Hubs Capture avro/parquet
    github/billing-usage/   # ai_credit + premium_request usage
    github/metrics/         # downloaded metric report files
    github/seats/           # daily seat snapshots
    anthropic/usage/
    google/billing/
    cursor/usage/
    databricks/usage/
    aws/cur/
    gcp/billing/
    _meta/                  # ingestion manifests, checksums, batch IDs
```

### What lands here

-   <mark>Batch sources</mark> (billing exports, API pulls): each connector writes raw files verbatim plus an ingestion-metadata envelope (source, timestamp, batch ID, checksum) — the Bronze contract from [the schema doc](02.000-bronze-silver-gold-schemas.md).
-   <mark>Streaming sources</mark> (gateway/app telemetry): Event Hubs with <mark>Capture</mark> enabled writes batched Avro/Parquet straight into `azure/gateway/`, so streaming and batch converge in the same Bronze store.

### Rules

-   Append-only and immutable; no transformation in Bronze.
-   Lifecycle-managed: cool/archive tiers and retention per dataset.
-   Idempotent by `source_file_etag_or_hash` so re-runs don't duplicate.

## 🥈 Silver layer

Silver is a set of <mark>.NET transformation jobs and APIs</mark> that turn raw Bronze files into the canonical entities. Each stage is idempotent and re-runnable, triggered by Bronze availability (a queue message or a schedule).

### Processing stages

| Stage (step name) | Responsibility |
|---|---|
| `SilverNormalize` | Parse, dedupe, and standardize each source's raw records. |
| `SilverEnrich` | Resolve identity (principal → user → team → org via directory SCD2) and client IP → network zone. |
| `SilverConform` | Map every source into the canonical FOCUS-shaped `fact_cloud_cost` and canonical `fact_ai_usage`. |
| `SilverKeys` | Compute `cost_bucket_key` and assign conformed dimension surrogate keys. |
| `SilverQuality` | Set malformed/retry flags, confidence scores, and reconciliation checks. |

### Output

Silver writes canonical Parquet back to a `silver/` zone (rebuildable) and/or staging tables in Azure SQL. The canonical outputs are exactly the entities defined in [the schema doc](02.000-bronze-silver-gold-schemas.md): `fact_cloud_cost`, `fact_ai_usage`, and conformed dimension staging.

### APIs

Some processing is request-driven rather than batch — for example, a directory-lookup API or a taxonomy-mapping API used by both Silver jobs and the Admin app. These live alongside the jobs as small .NET services.

## 🥇 Gold layer

Gold is <mark>**multi-target**</mark>. The star schema is the stable contract; the other targets are additive serving surfaces for different query patterns.

| Target | Role in AICM | Strength | Use when |
|---|---|---|---|
| <mark>Azure SQL Database</mark> (star schema) | Canonical facts + dims + `fact_cost_allocation`; chargeback marts | Dimensional joins, row-level security, mature BI | Always — the v1 backbone |
| <mark>Azure Data Explorer (Kusto)</mark> | High-volume raw/near-real-time telemetry, time-series deep dives | Fast ingest, KQL, high cardinality | Request-level analytics, anomaly detection |
| <mark>Log Analytics</mark> workspace | Turnkey operational dashboards | Workbooks, alerts, no schema to manage | Ops/DQ dashboards without a BI build |
| <mark>Power BI</mark> semantic model | Business reporting over SQL (and/or Kusto) | Chargeback, unit economics, self-service | All personas |

### Gold loaders

The allocation engine runs first, then per-target loaders fan out:

-   `GoldAllocate` — the allocation waterfall that fills `fact_cost_allocation` (every dollar allocated once).
-   `GoldLoadSql` — upserts facts/dims/marts into the Azure SQL star schema.
-   `GoldLoadKusto` — streams request-grain telemetry into Kusto tables.
-   `GoldLoadLogAnalytics` — optional; ships curated telemetry to a Log Analytics workspace for Workbooks.
-   `GoldBuildMarts` — materializes the FinOps/engineering/governance marts.

> Because the canonical model is defined once, adding Kusto or Log Analytics is a new loader, not a redesign. The same is true when a future phase adds a Fabric Warehouse with Direct Lake.

## 🔌 Source connectors

Every source is a <mark>pluggable connector</mark> behind one contract (`IBronzeConnector`): authenticate, pull or receive, land raw to Bronze with the ingestion envelope. v1 targets a broad set; each is an independent deployable step.

| Provider | Datasets | Ingestion | Bronze step |
|---|---|---|---|
| Azure billing | Cost Management / FOCUS export | Batch (daily) | `BronzeAzureBilling` |
| Azure AI / Foundry | Gateway + app telemetry | Streaming (Event Hubs) | `BronzeGatewayStream` |
| GitHub Copilot | Billing usage, metrics reports, seats | Batch (daily) | `BronzeGithubBilling`, `BronzeGithubMetrics`, `BronzeGithubSeats` |
| Anthropic Claude | CCU / usage | Batch | `BronzeClaudeUsage` |
| Google | Vertex / Gemini / AI Studio usage + billing | Batch | `BronzeGoogleUsage` |
| Cursor | Team usage/admin export | Batch | `BronzeCursorUsage` |
| Databricks | Genie / model-serving usage | Batch | `BronzeDatabricksUsage` |
| AWS | Cost and Usage Report (CUR) | Batch | `BronzeAwsCur` |
| GCP | Billing export (BigQuery) | Batch | `BronzeGcpBilling` |

Each connector maps only to the shared Bronze contract; provider quirks (auth, pagination, formats) stay inside the connector. Silver's `SilverConform` is where each raw shape becomes canonical.

## 🧩 Compute, hosting, and orchestration

### v1 hosting

-   <mark>Batch jobs</mark> (`Bronze*`, `Silver*`, `Gold*`) run as <mark>WebJobs on App Service</mark>, triggered by schedule (CRON) or a Storage/Service Bus queue message.
-   <mark>Streaming</mark> uses <mark>Event Hubs</mark> + Capture into Bronze; an Event Hubs-triggered processor (`BronzeGatewayStream`) handles any inline shaping.
-   <mark>Admin app</mark> (`AdminApp.Api` + `AdminApp.Client`) runs on <mark>App Service</mark>.

### Orchestration

For v1, keep it lightweight: a queue-driven pipeline (Service Bus) where each stage enqueues the next, plus a scheduler for pulls. When dependencies grow, adopt <mark>Durable Functions</mark> or <mark>Azure Data Factory</mark> pipelines for orchestration without rewriting the stage logic.

### Scale-out path

The hosting and compute are deliberately swappable:

-   <mark>Hosting</mark>: App Service + WebJobs → Azure Functions + Container Apps → AKS.
-   <mark>Heavy Silver</mark>: .NET → Microsoft Fabric (Lakehouse + notebooks/pipelines) or Azure Databricks when volume grows past low/medium.
-   <mark>Serving</mark>: Azure SQL → add Fabric Warehouse + Direct Lake for BI at scale.

## 🏷️ Naming conventions and processing steps

Consistent names make the pipeline self-describing.

### Conventions

-   <mark>Processing steps (deployable jobs)</mark>: PascalCase.
    -   Bronze: `Bronze<Provider><Dataset>` (for example `BronzeAzureBilling`, `BronzeGithubMetrics`).
    -   Silver: `Silver<Verb>` (for example `SilverNormalize`, `SilverConform`).
    -   Gold: `Gold<Verb>` (for example `GoldAllocate`, `GoldLoadSql`).
-   <mark>.NET projects/assemblies</mark>: `Aicm.<Layer>.<Area>` (for example `Aicm.Bronze.GitHub`, `Aicm.Gold.Sql`).
-   <mark>Admin app</mark>: `AdminApp.<Tier>` (`AdminApp.Api`, `AdminApp.Client`, `AdminApp.Shared`).
-   <mark>Hosts</mark>: `Aicm.Host.<Runtime>` (`Aicm.Host.WebJobs` now, `Aicm.Host.Functions` later).
-   <mark>Bronze storage paths</mark>: lowercase kebab (`github/billing-usage`).
-   <mark>Gold DB objects</mark>: `fact_*`, `dim_*`, `mart_*` (from the schema doc).

### Step registry (v1)

| Layer | Steps |
|---|---|
| Bronze (batch) | `BronzeAzureBilling`, `BronzeGithubBilling`, `BronzeGithubMetrics`, `BronzeGithubSeats`, `BronzeClaudeUsage`, `BronzeGoogleUsage`, `BronzeCursorUsage`, `BronzeDatabricksUsage`, `BronzeAwsCur`, `BronzeGcpBilling` |
| Bronze (stream) | `BronzeGatewayStream` |
| Silver | `SilverNormalize`, `SilverEnrich`, `SilverConform`, `SilverKeys`, `SilverQuality` |
| Gold | `GoldAllocate`, `GoldLoadSql`, `GoldLoadKusto`, `GoldLoadLogAnalytics`, `GoldBuildMarts` |
| Quality | `QualityReconcile` (per-bucket billing-vs-allocation identity) |
| Apps | `AdminApp.Api`, `AdminApp.Client` |

## 🗂️ Repository and solution structure

One .NET solution (monorepo) with clear layer boundaries, an infra folder, and a versioned contracts area.

``` text
aicm/
    src/
        bronze/
            Aicm.Bronze.Abstractions      # IBronzeConnector, landing contract
            Aicm.Bronze.Azure             # BronzeAzureBilling
            Aicm.Bronze.Gateway           # BronzeGatewayStream (Event Hubs)
            Aicm.Bronze.GitHub            # BronzeGithubBilling/Metrics/Seats
            Aicm.Bronze.Anthropic
            Aicm.Bronze.Google
            Aicm.Bronze.Cursor
            Aicm.Bronze.Databricks
            Aicm.Bronze.Aws
            Aicm.Bronze.Gcp
        silver/
            Aicm.Silver.Core              # stage pipeline, canonical entities
            Aicm.Silver.Normalize
            Aicm.Silver.Enrich            # identity + network
            Aicm.Silver.Conform           # FOCUS canonical mapping
            Aicm.Silver.Quality
        gold/
            Aicm.Gold.Allocation          # GoldAllocate (waterfall)
            Aicm.Gold.Sql                 # star-schema loader
            Aicm.Gold.Kusto
            Aicm.Gold.LogAnalytics
            Aicm.Gold.Marts
        shared/
            Aicm.Core                     # domain, canonical model, dims
            Aicm.Contracts                # generated types from /contracts
            Aicm.Storage                  # ADLS/Blob abstractions
            Aicm.Messaging                # Event Hubs / Service Bus
            Aicm.Identity                 # Entra, managed identity, SCD2 lookups
        apps/
            AdminApp.Api
            AdminApp.Client
            AdminApp.Shared
        hosts/
            Aicm.Host.WebJobs             # v1 batch host (App Service)
            Aicm.Host.Functions           # future
    contracts/                            # versioned, not code
        schemas/{canonical,providers}/
        taxonomy/{request-types,model-families,processing-types}/
        allocation-rules/
    infra/                                # Bicep or Terraform
        modules/ envs/{dev,test,prod}/
    quality/                              # reconciliation + data tests
    tests/
    docs/                                 # runbooks, data dictionary
```

This mirrors the medallion boundaries in code, keeps every connector isolated, and puts the canonical contracts under version control (per the schema doc's `contracts` guidance).

## 🖥️ Admin application

`AdminApp` is the control plane, not a data-path component. It has two tiers:

-   <mark>`AdminApp.Api`</mark> — a .NET API over configuration and operations: register connectors and credentials (via Key Vault references), edit allocation rules and taxonomies (writing to `contracts`), map cost centers to `dim_organization`, trigger reprocessing, and read ingestion/reconciliation status.
-   <mark>`AdminApp.Client`</mark> — the UI (Blazor or SPA) for FinOps and platform admins: connector health, batch/stream status, reconciliation and data-quality dashboards, unattributed-cost and unknown-taxonomy monitors, and rule/taxonomy editing.

It reads Gold (Azure SQL) for status and writes only to configuration and the `contracts` store — never to Bronze/Silver data.

## ⚖️ Options compared

### Silver compute

| Option | Best for | Pros | Cons | AICM fit |
|---|---|---|---|---|
| <mark>.NET workers + Functions</mark> | Low/medium volume, .NET team | Full control, low cost, matches skills, easy testing | You own retry/orchestration | **v1 choice** |
| Microsoft Fabric | Unified analytics + BI | Notebooks + pipelines + Direct Lake, low ops | SaaS cost, less code control | Future scale-out |
| Azure Databricks | Very high volume Spark | Scale, Delta, ML | Cost, Spark skills | Only if > ~1B events |
| ADF / Synapse | Low-code ETL | Visual, many connectors | Limited custom logic | Orchestration aid |

### Gold serving

| Target | Query pattern | Trade-off |
|---|---|---|
| <mark>Azure SQL star</mark> | Chargeback, dimensional BI | Best modeling + RLS; not ideal for billions of raw events |
| <mark>Log Analytics</mark> | Ops dashboards + alerts | Turnkey Workbooks; less flexible than a BI model |
| Kusto (ADX) | Event/time-series analytics | Blazing ingest + KQL; not a dimensional model |
| Fabric Warehouse | Unified BI at scale | Direct Lake performance; requires Fabric adoption |

### Ingestion latency

| Mode | Sources | Mechanism |
|---|---|---|
| Batch | Billing exports, API pulls (Copilot, Cursor, Claude, Google, Databricks, AWS/GCP) | Scheduled WebJob/Function → Bronze |
| Streaming | Gateway/app telemetry | Event Hubs + Capture → Bronze (optional Stream Analytics) |

## 🔒 Cross-cutting concerns

-   <mark>Identity and secrets</mark>: managed identity + Microsoft Entra everywhere; connector credentials and API keys in <mark>Key Vault</mark> (referenced, never in config).
-   <mark>Configuration</mark>: canonical schemas, taxonomies, and allocation rules live in versioned `contracts`; code binds to generated types.
-   <mark>Observability</mark>: Application Insights for the jobs/apps; a Log Analytics workspace for platform telemetry and Workbooks; per-stage batch IDs for lineage.
-   <mark>Idempotency and reprocessing</mark>: every stage keyed by batch ID/checksum; rule-versioned reprocessing rebuilds historical months from Bronze.
-   <mark>Cost efficiency</mark>: ADLS lifecycle tiers, serverless/elastic Azure SQL where possible, and pay-as-you-go Event Hubs sized to the low/medium volume target.
-   <mark>Security</mark>: least-privilege RBAC per connector, private endpoints for storage/SQL, and row-level security on chargeback marts.

## 🚀 Phased rollout and evolution

1.  <mark>Phase 1 — foundation (v1)</mark>: App Service + WebJobs; connectors for Azure billing, Foundry gateway telemetry, and GitHub Copilot; ADLS Bronze; .NET Silver; Azure SQL Gold + Power BI; first Event Hubs stream.
2.  <mark>Phase 2 — breadth + telemetry</mark>: add Claude, Google, Cursor, Databricks, AWS, and GCP connectors; add Kusto for request-grain telemetry and Log Analytics Workbooks; full allocation engine and reconciliation gates.
3.  <mark>Phase 3 — scale-out</mark>: move heavy Silver to Fabric or Databricks; shift hosting to Functions + Container Apps or AKS; add Fabric Warehouse + Direct Lake for BI. The canonical model and step names stay unchanged.

## ✅ Key decisions

| Concern | v1 choice | Future path |
|---|---|---|
| Silver compute | .NET workers + Azure Functions | Microsoft Fabric / Databricks |
| Hosting | App Service + WebJobs | Functions + Container Apps, or AKS |
| Bronze store | ADLS Gen2 storage account | + OneLake (Fabric) |
| Ingestion | Batch + streaming (Event Hubs) | more streaming |
| Gold serving | Azure SQL star + Power BI (+ Kusto; Log Analytics optional) | Fabric Warehouse + Direct Lake |
| v1 sources | Azure billing, Foundry telemetry, GitHub Copilot | Claude, Google, Cursor, Databricks, AWS, GCP |
| Volume target | Low/medium (< ~10M events/month) | scale-out layers above |
