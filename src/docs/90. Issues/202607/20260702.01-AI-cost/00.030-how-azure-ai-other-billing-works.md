## 🎯 Scope: the non-generative AI streams

Not every AI cost is a token. Alongside Foundry's generative models, most enterprises run <mark>non-LLM AI services</mark> — the classic Azure AI Services (also surfaced as Foundry Tools) that do vision, speech, language, and document work. Their billing follows a different logic, and mixing them up with token metering is a common source of reconciliation error.

This article covers the billing mechanics for:

-   <mark>Azure AI Vision</mark> — image analysis and OCR.
-   <mark>Document Intelligence</mark> — structured extraction from documents.
-   <mark>Azure AI Language</mark> — sentiment, key phrases, entities, language detection.
-   <mark>Azure AI Translator</mark> — text and document translation.
-   <mark>Azure AI Speech</mark> — speech-to-text and text-to-speech.
-   <mark>Azure AI Content Safety</mark> — text and image moderation and guardrails.
-   <mark>Azure Content Understanding</mark> — multimodal extraction that blends transaction and token billing.

For generative model and search billing, see [How Azure AI billing works](00.010-how-azure-ai-billing-works.md).

## 🧭 The transaction-based billing model

The defining trait of these services is <mark>transaction (volume) billing</mark>: you pay per unit of work processed — an image, a page, a text record, a character, or a minute of audio — not per token.

That has three consequences for cost analysis:

1.  <mark>Cost is directly proportional to volume</mark>, which makes pay-as-you-go easy to forecast from throughput.
2.  <mark>Each service defines its own unit</mark>, so there's no single "AI unit" across them — the canonical model must normalize each.
3.  <mark>Billing carries no user identity</mark>, exactly like cloud billing. Attribution to a user or team must come from gateway/application telemetry that records the caller alongside the transaction.

## 📇 Billing units by service

Each service meters a specific unit. Rates vary by service, feature, and tier — always confirm current rates on the pricing page — but the *unit* is what your canonical model needs.

| Service | Billing unit | Notes |
|---|---|---|
| Azure AI Vision | Per 1,000 transactions | Image analysis and OCR (Read) features |
| Document Intelligence | Per 1,000 pages | Rate varies by model: read, layout, prebuilt, custom |
| Azure AI Language | Per 1,000 text records | One text record = up to 1,000 characters |
| Azure AI Translator | Per character (quoted per million) | Text translation; document translation on paid tiers |
| Azure AI Speech (STT) | Per hour (or minute) of audio | Speech-to-text transcription |
| Azure AI Speech (TTS) | Per 1 million characters | Neural text-to-speech |
| Content Safety (text) | Per text record | One record is a fixed character block |
| Content Safety (image) | Per image | Priced by number of images submitted |

Two units trip people up most often:

-   <mark>Text records</mark> (Language and Content Safety) are quantized. A 1,500-character document is two text records, not 1.5 — units round up to the block size.
-   <mark>Characters</mark> (Translator, Speech TTS) are counted on the processed content, so long inputs scale cost linearly and predictably.

## 📄 Document processing and Content Understanding

Document-centric billing deserves its own note because it mixes tiers and, in the newer service, modalities.

### Document Intelligence

Billing is <mark>per 1,000 pages</mark>, with the rate depending on the model you invoke:

-   <mark>Read</mark> — basic OCR text extraction.
-   <mark>Layout</mark> — text plus tables and structure.
-   <mark>Prebuilt</mark> — domain models (invoices, receipts, IDs).
-   <mark>Custom</mark> — models you train.

### Content Understanding

<mark>Azure Content Understanding</mark> is a multimodal analyzer that blends two charge types, so it straddles this article and the token world of [Foundry model billing](00.010-how-azure-ai-billing-works.md):

1.  <mark>Content extraction</mark> (transaction-based):
    -   Documents — per 1,000 pages, across three tiered meters (minimal for digital files, basic for OCR, standard for layout). You're charged for the *work actually performed* on each page, not the analyzer you call.
    -   Audio and video — per minute (speech-to-text, plus frame/shot processing for video).
    -   Images — no separate content-extraction charge.
2.  <mark>Generative features</mark> (token-based):
    -   Contextualization tokens for grounding, confidence, and formatting.
    -   LLM input/output tokens and embeddings — billed on the <mark>Foundry model deployment you provide</mark>, so that usage appears on your Foundry bill, not on the Content Understanding meter.

Its total cost follows:

$$
\text{Total} = \text{extraction} + \text{contextualization} + \text{LLM input} + \text{LLM output} + \text{embeddings}
$$

That split matters for the platform: a single Content Understanding call produces both a transaction meter *and* Foundry token meters on a different resource, which must be correlated to see true cost.

## 💵 Commitment tiers and disconnected containers

For steady, high-volume workloads, standard pay-as-you-go isn't the only option.

### Commitment tier pricing

<mark>Commitment tiers</mark> let you commit to a fixed volume for a fixed fee, at a discount to pay-as-you-go, giving predictable total cost. Commitment tiers are available for:

-   Speech-to-text (Standard) and Text-to-speech (Neural).
-   Text Translation (Standard).
-   Language Understanding and Azure AI Language features (sentiment, key phrase extraction, language detection, named entity recognition).
-   Vision OCR (Read).
-   Document Intelligence (Custom and Invoice).

A crucial constraint: <mark>commitment tiers require a single-service resource</mark> (for example a dedicated Speech or Translator resource). You **can't** use commitment pricing on a multi-service Foundry resource. Azure Advisor flags services with enough usage to benefit from a commitment tier.

### Disconnected containers

For on-premises or air-gapped use, <mark>disconnected containers</mark> run the service locally under an annual commitment charged upfront. You license projected usage for a calendar year and can add units pro-rata during the term. This turns a usage-based service into a fixed annual cost — an important distinction when the platform reconciles it.

## 🧬 Resource type changes how cost is attributed

Non-LLM services can be deployed as either a <mark>multi-service</mark> resource (one Foundry/Azure AI Services resource fronting many capabilities) or a <mark>single-service</mark> resource (a dedicated Speech, Translator, Vision, or similar resource). The choice affects your cost data:

| Aspect | Multi-service resource | Single-service resource |
|---|---|---|
| Meter attribution | Multiple services share one resource; meters distinguish the service | One resource maps cleanly to one service |
| Commitment tiers | Not available | Available |
| Resource-group split | Coarser (shared resource) | Finer (per-service resource) |

For clean attribution, single-service resources give you a tighter resource-to-service mapping in `fact_cloud_cost`; multi-service resources need meter-level splitting to separate the capabilities.

## 📊 How these costs appear in Cost Management

In Cost Management, group by **Resource** then by **Meter**:

-   Each service's transactions appear under <mark>service-specific meters</mark> (for example OCR, neural TTS, translated characters).
-   <mark>Commitment tiers</mark> appear as a fixed recurring charge rather than variable transaction lines.
-   <mark>Disconnected containers</mark> show a single upfront annual charge.
-   For disconnected usage, billing metadata such as `CognitiveServices.TextTranslation.Container.TranslatedCharacters` counts consumption against your licensed volume.

As always, the invoice and meters are the source of truth; HTTP status codes don't determine whether a request was billed.

## 🧱 What this means for attribution

These services share cloud billing's blind spot: no user, no request type. But their transaction telemetry is easy to correlate when the gateway records the caller.

| Billing fact | Lands in | Attribution source needed |
|---|---|---|
| Per-transaction meters (Vision, Language, Content Safety) | `fact_cloud_cost` | Gateway telemetry: caller + transaction count |
| Per-page meters (Document Intelligence) | `fact_cloud_cost` | Application telemetry: user/job + page count |
| Per-character / per-minute meters (Translator, Speech) | `fact_cloud_cost` | App telemetry: user + processed volume |
| Commitment tier (fixed) | `fact_cloud_cost` | Consuming workload weighting to spread flat cost |
| Content Understanding token portion | `fact_cloud_cost` (Foundry resource) | Correlate call ID across the two resources |

The pattern mirrors the generative side: <mark>pay-as-you-go transaction meters attribute proportionally</mark>, while <mark>commitment tiers and container licenses are flat</mark> and must be spread across consumers using telemetry weights inside each Cost Management bucket. Add each service's unit to the platform's `dim_processing_type` taxonomy (text, image, audio, translation, document) so non-LLM spend rolls up alongside model spend.

## ✅ Key takeaways

-   Non-LLM Azure AI services bill by **transaction/volume** — images, pages, text records, characters, or minutes — not by tokens.
-   **Each service defines its own unit**, so the canonical model must normalize them into a shared processing-type taxonomy.
-   **Content Understanding** blends transaction extraction with **Foundry token charges** that land on a separate resource — correlate them to see true cost.
-   **Commitment tiers** (single-service resources only) and **disconnected containers** convert variable usage into predictable or upfront fixed cost.
-   Like cloud billing, these meters carry **no user identity**; gateway/application telemetry supplies the attribution the platform needs.
